## 1. Назначение и состав системы

roversim — программный стенд для разработки и проверки алгоритмов автономной
навигации колёсного робота с дифференциальным приводом. Стенд решает три задачи:

* воспроизводимо моделировать движение робота и показания его сенсоров быстрее
  реального времени на три порядка — для массового обучения с подкреплением;
* служить «железом» для классического навигационного стека (SLAM, глобальный и
  локальный планировщики), которому доступны только показания сенсоров;
* давать количественные метрики качества навигации: долю достигнутых целей,
  число столкновений, SPL, ошибку локализации.

Поток данных:

```
            уставки колёс (левое, правое), рад/с
   ┌──────────────────────────────────────────────────────────┐
   │                                                          ▼
┌──┴───────────────┐    ┌─────────────────────────────────────────────────┐
│  управление      │    │ Simulator                                       │
│                  │    │   World ── сетка занятости, препятствия         │
│  NavigationAgent │    │   DiffDrive ── динамика привода, контакты       │
│  (SLAM, Theta*,  │    │   подвижные препятствия                         │
│   DWA)           │    │   Lidar2D, Imu, WheelOdometry ── сенсоры с шумом│
│  или политика    │    │   задача: цель, награда, завершение             │
│  PPO             │    └───────────────┬─────────────────────────────────┘
└──▲───────────────┘                    │ буферы наблюдений (без копирования):
   │                                    │   lidar  f32[num_rays]
   │   в процессе (pybind11) или        │   proprio f32[15]  IMU, одометрия, цель
   │   через разделяемую память         │   state  f64[12]   истинное состояние
   └────────────────────────────────────┘
```

Ядро — статическая библиотека на C++20 без внешних зависимостей
(`core/`). Поверх неё: Python-модуль (`python/bindings.cpp`, pybind11),
исполняемые файлы `roversim_server`, `roversim_bench` и `roversim_nav_bench`
(`apps/`), тесты (`tests/`).

**Выбор языка.** Для ядра рассматривались C++20 и Rust; оба дают одинаковый
машинный код и предсказуемое время выполнения. Выбран C++20 по двум причинам.
Во-первых, центральные механизмы проекта — буферы наблюдений, в которые
симулятор пишет, а внешний код читает без копирования, и разделяемая между
процессами память — по своей природе лежат вне модели заимствований Rust и
потребовали бы `unsafe` в самых нагруженных местах; в C++ они выражаются
напрямую. Во-вторых, экосистема робототехники (ROS 2, Eigen, MuJoCo, pybind11)
ориентирована на C++. Преимущество Rust — строгая семантика плавающей точки по
умолчанию — в C++ достигается флагом компилятора (раздел 6.5).

## 2. Обозначения и параметры

**Системы координат.** Мировая СК $W$ — правая, ось $z$ вверх. Связанная СК
робота $B$: начало в середине ведущей оси, ось $x$ вперёд, ось $y$ влево. СК
сенсора $S$ задана позой установки относительно $B$. Поза робота —
$(x, y, \theta)$, угол $\theta$ отсчитывается против часовой стрелки от оси $x_W$.

**Состояние.** Скорость корпуса задаётся в связанной СК: продольная $v_x$,
поперечная $v_y$, угловая $\omega$. Колёса: угловые скорости $\omega_L$,
$\omega_R$ и накопленные углы $\varphi_L$, $\varphi_R$.

| Обозначение | Смысл | Значение по умолчанию | Поле конфигурации |
| --- | --- | --- | --- |
| $R$ | радиус корпуса (круг столкновений) | 0.20 м | `robot.radius` |
| $r$ | радиус колеса | 0.05 м | `robot.wheel_radius` |
| $b$ | колея | 0.30 м | `robot.track_width` |
| $m$ | масса | 10 кг | `robot.mass` |
| $I_z$ | момент инерции корпуса | 0.20 кг·м² | `robot.inertia_z` |
| $I_w$ | момент инерции колеса с приведённым ротором | 2·10⁻³ кг·м² | `robot.wheel_inertia` |
| $K$ | жёсткость привода скорости | 0.5 Н·м·с/рад | `robot.motor_gain` |
| $\tau_{\max}$ | предельный момент на колесе | 0.6 Н·м | `robot.motor_max_torque` |
| $\omega_{\max}$ | предельная уставка скорости колеса | 20 рад/с | `robot.max_wheel_speed` |
| $\mu_\parallel$, $\mu_\perp$ | продольное и поперечное трение шин | 0.8, 0.9 | `robot.mu_long`, `robot.mu_lat` |
| $C_{rr}$ | коэффициент сопротивления качению | 0.015 | `robot.rolling_resistance` |
| $c_v$, $c_\omega$ | вязкое сопротивление | 0.4 Н·с/м, 0.02 Н·м·с/рад | `robot.linear_drag`, `robot.angular_drag` |
| $\Delta t$ | шаг физики | 5 мс | `physics_dt` |
| $T$ | период управления и опроса сенсоров | 50 мс (10 шагов физики) | `physics_dt * substeps` |

Отсюда предельные скорости качения без проскальзывания:
$v_{\max} = r\,\omega_{\max} = 1.0$ м/с, $\;\Omega_{\max} = 2 v_{\max} / b = 6.67$ рад/с.

## 3. Модель движения робота

Реализация: `core/src/robot.cpp` (динамика и решатель), `core/src/world.cpp`
(обнаружение столкновений), `core/src/simulator.cpp` (шаг по времени).

### 3.1. Кинематика дифференциального привода

При качении без проскальзывания скорости точек контакта колёс равны
окружным скоростям ободов: $v_x \mp \omega b/2 = r\,\omega_{L,R}$. Отсюда прямая
и обратная кинематика:

$$
v_x = \frac{r(\omega_R + \omega_L)}{2}, \qquad
\omega = \frac{r(\omega_R - \omega_L)}{b};
\qquad\qquad
\omega_L = \frac{v_x - \omega b/2}{r}, \qquad
\omega_R = \frac{v_x + \omega b/2}{r}.
$$

Робот движется по дуге вокруг мгновенного центра вращения, лежащего на оси
колёс на расстоянии

$$
\rho = \frac{v_x}{\omega} = \frac{b}{2}\cdot\frac{\omega_R + \omega_L}{\omega_R - \omega_L}
$$

от середины оси. Поза подчиняется уравнениям

$$
\dot x = v_x\cos\theta - v_y\sin\theta,\qquad
\dot y = v_x\sin\theta + v_y\cos\theta,\qquad
\dot\theta = \omega,
$$

а неголономная связь «колесо не скользит вбок» записывается как $v_y = 0$, то
есть $-\dot x\sin\theta + \dot y\cos\theta = 0$.

**Насыщение.** Функция обратной кинематики `DiffDrive::twist_to_wheels`
ограничивает уставки значением $\omega_{\max}$, умножая обе на общий
коэффициент: отношение $\omega_R/\omega_L$, а с ним и радиус дуги $\rho$,
сохраняется.

**Точное интегрирование позы.** Если на шаге $\Delta t$ скорости
$(v_x, v_y, \omega)$ в связанной СК постоянны, движение — винтовое на плоскости
(экспоненциальное отображение группы $SE(2)$). При $\phi = \omega\Delta t$

$$
\begin{pmatrix}\Delta x_B\\ \Delta y_B\end{pmatrix}
= \Delta t
\begin{pmatrix}
\dfrac{\sin\phi}{\phi} & -\dfrac{1-\cos\phi}{\phi}\\[2mm]
\dfrac{1-\cos\phi}{\phi} & \dfrac{\sin\phi}{\phi}
\end{pmatrix}
\begin{pmatrix}v_x\\ v_y\end{pmatrix},
\qquad
\begin{pmatrix}x\\ y\end{pmatrix} \leftarrow
\begin{pmatrix}x\\ y\end{pmatrix} + \mathbf R(\theta)\begin{pmatrix}\Delta x_B\\ \Delta y_B\end{pmatrix},
\qquad \theta \leftarrow \theta + \phi.
$$

При $|\phi| < 10^{-4}$ используются ряды $\sin\phi/\phi \approx 1 - \phi^2/6$,
$(1-\cos\phi)/\phi \approx \phi/2 - \phi^3/24$. Робот идёт по дуге, а не по
хорде, поэтому при постоянных скоростях колёс траектория совпадает с
аналитической с точностью до округления (тест `kinematics_follows_exact_arc`:
расхождение менее $10^{-9}$ м за 3 с движения).

### 3.2. Динамика

Корпус и колёса связаны не кинематически, а силами трения в пятнах контакта.
Это позволяет моделировать пробуксовку, занос и упор в препятствие в рамках
одних и тех же уравнений.

Уравнения корпуса в связанной (вращающейся) СК:

$$
\begin{aligned}
m(\dot v_x - \omega v_y) &= F_L + F_R - C_{rr}\,m g\,\operatorname{sign}(v_x) - c_v v_x + \textstyle\sum_k \lambda_k n_{k,x},\\
m(\dot v_y + \omega v_x) &= F_\perp - c_v v_y + \textstyle\sum_k \lambda_k n_{k,y},\\
I_z\,\dot\omega &= \tfrac{b}{2}(F_R - F_L) - c_\omega\,\omega,
\end{aligned}
$$

где $F_{L,R}$ — продольные силы тяги шин, $F_\perp$ — суммарная поперечная сила
трения оси, $\lambda_k \ge 0$ — нормальные реакции стен с нормалями $\mathbf n_k$
(корпус — круг с центром в начале $B$, поэтому реакции не создают момента).

Уравнение вращения колеса $i \in \{L, R\}$ и закон привода:

$$
I_w\,\dot\omega_i = \tau_i - r F_i,\qquad
\tau_i = \operatorname{clamp}\bigl(K(\omega_i^{*} - \omega_i),\ -\tau_{\max},\ \tau_{\max}\bigr),
$$

где $\omega_i^{*}$ — уставка (управляющее воздействие). Это сервопривод скорости
с ограничением момента; при $K = \tau_{\text{stall}}/\omega_{\text{noload}}$ он
совпадает с линейной механической характеристикой коллекторного двигателя с
ограничением тока.

Трение шин — закон Кулона. Проскальзывание колеса
$s_i = r\omega_i - v_i^{c}$, где $v_L^{c} = v_x - \omega b/2$,
$v_R^{c} = v_x + \omega b/2$ — скорость корпуса в точке контакта:

$$
|F_i| \le \mu_\parallel N_i,\quad N_i = \tfrac{1}{2} m g;\qquad
s_i = 0 \ \text{при}\ |F_i| < \mu_\parallel N_i,\qquad
F_i = \mu_\parallel N_i \operatorname{sign}(s_i)\ \text{иначе}.
$$

Аналогично для поперечного направления: $|F_\perp| \le \mu_\perp m g$, причём
$v_y = 0$, пока предел не достигнут.

**Следствие: модель без проскальзывания.** Пока обе шины в сцеплении,
подстановка $F_i = (\tau_i - I_w\dot\omega_i)/r$ даёт

$$
\Bigl(m + \frac{2 I_w}{r^2}\Bigr)\dot v_x = \frac{\tau_L + \tau_R}{r} - C_{rr} m g - c_v v_x,
\qquad
\Bigl(I_z + \frac{I_w b^2}{2 r^2}\Bigr)\dot\omega = \frac{b(\tau_R - \tau_L)}{2r} - c_\omega\omega .
$$

При параметрах по умолчанию разгон с места на насыщенных приводах равен
$(2\tau_{\max}/r - C_{rr} m g)/(m + 2I_w/r^2) = (24 - 1.47)/11.6 = 1.94$ м/с².
Симуляция воспроизводит это значение (тест `acceleration_matches_newton`).
Требуемая тяга $12$ Н на колесо меньше предела сцепления
$\mu_\parallel N = 39$ Н, поэтому на обычном покрытии робот не буксует; при
$\mu_\parallel = 0.05$ («лёд») корпус разгоняется с ускорением
$(\mu_\parallel - C_{rr})g$, а колёса раскручиваются до уставки (тест
`wheels_slip_when_traction_is_low`).

### 3.3. Дискретизация: шаг на уровне скоростей и импульсов

Система жёсткая: постоянная времени привода $I_w/K = 4$ мс сравнима с шагом
физики, а закон Кулона разрывен. Явные схемы здесь неустойчивы, а регуляризация
трения вносит паразитное «ползучее» проскальзывание. Поэтому используется схема
Стюарта — Тринкла [1, 2]: неизвестными служат скорости в конце шага и импульсы
сил за шаг, а трение и контакты записываются как ограничения с неравенствами.
Один шаг `DiffDrive::step` состоит из трёх частей.

**1. Предиктор (явные силы).**

$$
v_x \leftarrow v_x + \Delta t\,\omega v_y,\qquad
v_y \leftarrow v_y - \Delta t\,\omega v_x
$$

— кориолисовы слагаемые вращающейся СК; затем сопротивление качению
$v_x \leftarrow \operatorname{sign}(v_x)\max(0, |v_x| - C_{rr} g\,\Delta t)$
(тормозит, но не меняет знак скорости) и вязкое сопротивление в неявной форме
$v \leftarrow v/(1 + \Delta t\,c_v/m)$, $\omega \leftarrow \omega/(1 + \Delta t\,c_\omega/I_z)$.

**2. Связи.** Обозначим $J_i$ импульс тяги шины $i$ за шаг (приложен к корпусу;
к ободу — противоположный). Вращение колеса интегрируется неявным методом Эйлера:

$$
I_w(\omega_i^{+} - \omega_i) = \Delta t\,\operatorname{clamp}\bigl(K(\omega_i^{*} - \omega_i^{+}),\ \pm\tau_{\max}\bigr) - r J_i .
$$

Правая часть монотонна по $\omega_i^{+}$, поэтому решение единственно и находится
в замкнутой форме: сначала линейный режим

$$
\omega_i^{\text{lin}}(J_i) = \frac{I_w\omega_i + \Delta t K\,\omega_i^{*} - r J_i}{I_w + \Delta t K},
$$

и если соответствующий момент $K(\omega_i^{*} - \omega_i^{\text{lin}})$ выходит
за $\pm\tau_{\max}$, то $\omega_i^{+} = \omega_i + (\pm\Delta t\,\tau_{\max} - rJ_i)/I_w$.
Функция $\omega_i^{+}(J_i)$ непрерывна, кусочно-линейна и строго убывает;
изломы находятся в точках

$$
J_i^{\pm} = \frac{1}{r}\Bigl[\pm\,\Delta t\,\tau_{\max}\,\frac{I_w + \Delta t K}{\Delta t K} - I_w(\omega_i^{*} - \omega_i)\Bigr].
$$

Импульс $J_i$ изменяет скорость корпуса в точке контакта на $a\,J_i$, где
$a = 1/m + (b/2)^2/I_z$ — податливость корпуса. Закон Кулона для пятна контакта —
это поиск $J_i \in [-J_{\max}, J_{\max}]$, $J_{\max} = \mu_\parallel N_i \Delta t$,
обнуляющего проскальзывание в конце шага

$$
s_i(J_i) = r\,\omega_i^{+}(J_i) - \bigl(u_i + a\,(J_i - J_i^{0})\bigr),
$$

где $u_i$ — текущая скорость корпуса в точке контакта, $J_i^{0}$ — уже
приложенный импульс. Функция $s_i$ строго убывает и кусочно-линейна, поэтому
корень (или граница отрезка, если корня на нём нет) находится **точно**, без
итераций и без параметров регуляризации (`Wheel::solve`).

Остальные связи — стандартные проекции:

$$
J_\perp \leftarrow \operatorname{clamp}\bigl(J_\perp - m v_y,\ \pm\mu_\perp m g\,\Delta t\bigr),
\qquad
\lambda_k \leftarrow \max\Bigl(0,\ \lambda_k + m\bigl(-\tfrac{g_k}{\Delta t} - \mathbf n_k\!\cdot\!\mathbf v\bigr)\Bigr).
$$

Второе выражение — «упреждающий» контакт: при зазоре $g_k \ge 0$ сближаться со
стеной можно не быстрее $g_k/\Delta t$, так что к концу шага зазор не станет
отрицательным.

Связи перебираются по очереди (проекционный метод Гаусса — Зейделя), пока
наибольшее изменение скорости за проход не станет меньше $10^{-13}$ м/с (не более
32 проходов). Две колёсные связи взаимодействуют только через корпус,
коэффициент сжатия за проход равен $\bigl(a_{LR}/d\bigr)^2$, где
$a_{LR} = 1/m - (b/2)^2/I_z$, $d = r^2/(I_w + \Delta t K) + a$. При параметрах по
умолчанию это $(0.0125/0.768)^2 \approx 2.6\cdot10^{-4}$: в свободном движении
решатель сходится за 4–5 проходов (≈ 0.28 мкс на шаг физики).

Свойства схемы, проверяемые тестами:

* в режиме сцепления связи выполняются точно — путь, насчитанный по углам колёс,
  совпадает с путём точек контакта с точностью $10^{-9}$ м;
* схема устойчива при любом $\Delta t$ и не требует параметров сглаживания;
* когда тяги не хватает, импульс упирается в границу — получается буксование;
  когда робот упёрт в стену, колёса останавливаются, а реакция стены равна
  полной тяге $2\tau_{\max}/r = 24$ Н (тест `wall_stops_robot_without_penetration`).

**3. Интегрирование позы** по формулам раздела 3.1 с найденными скоростями
(полунеявная схема Эйлера: новые скорости — в обновление позы).

**Позиционная коррекция.** Условие непроникновения линейно по скорости, а поза
интегрируется по дуге, поэтому при движении с поворотом вплотную к стене корпус
может войти в неё на величину порядка $v\,\omega\,\Delta t^2/2$ (при
$v = 0.5$ м/с, $\omega = 2.3$ рад/с это $1.4\cdot10^{-5}$ м — измеренное значение
совпало с оценкой). После шага, если рядом были стены, положение проецируется на
допустимое множество (`Simulator::resolve_penetration`); тест
`robot_stays_inside_free_space_under_random_driving` подтверждает, что
проникновение не превышает $10^{-9}$ м.

### 3.4. Обнаружение столкновений

Мир — равномерная сетка занятости плюс аналитические препятствия
(прямоугольники, круги); край сетки считается стеной. Запрос
`World::collide_circle` возвращает контакты круга робота: единичную нормаль и
зазор.

Для занятой клетки определяется зона Вороного, в которой лежит центр круга:
грань (ближайшая точка — на ребре клетки) или вершина. Стена из нескольких
клеток должна вести себя как одно тело, поэтому контакты со скрытыми элементами
отбрасываются: с гранью, за которой находится соседняя занятая клетка, и с
вершиной, у которой занята хотя бы одна из двух смежных по грани клеток. Без
этого правила круг, скользящий вдоль ровной стены, получал бы ложные толчки на
стыках клеток (тест `collision_contacts_have_no_ghost_edges`: вдоль стены ровно
один контакт, нормаль строго перпендикулярна).

Широкая фаза использует поле расстояний (раздел 4.1): если до ближайшей занятой
клетки заведомо дальше $R$ плюс запас, перебор соседей пропускается.

### 3.5. Подвижные препятствия

Подвижные препятствия (`Simulator::move_obstacles`) — круги с постоянной по
модулю скоростью. На каждом шаге физики препятствие сдвигается на
$\mathbf u\,\Delta t$; если новая позиция пересекает стену, скорость зеркально
отражается от суммарной нормали контакта, $\mathbf u \leftarrow \mathbf u - 2(\mathbf u\cdot\mathbf n)\mathbf n$,
и поворачивается на малый случайный угол (чтобы траектории не замыкались в
короткие циклы). Так же препятствия отражаются друг от друга.

Взаимодействие с роботом устроено несимметрично. Схема расщеплённая: сначала
двигаются препятствия, затем робот. Для робота препятствие — обычный контакт с
зазором, вычисленным после его сдвига; робот не может въехать в препятствие, но
и не обязан отступать. Препятствие, которое упёрлось в робота, отражается и
остаётся на месте: оно не толкает робота (иначе могло бы вдавить его в стену).
Любое такое касание фиксируется как столкновение.

В статической карте мира подвижных препятствий нет: робот видит их только
лидаром.

## 4. Модели сенсоров

Реализация: `core/src/sensors.cpp`, трассировка лучей — `core/src/world.cpp`.

### 4.1. Лидар

**Геометрия.** Скан состоит из $N$ лучей с углами
$\alpha_i = \alpha_{\min} + i\,\Delta\alpha$ в СК сенсора,
$\alpha_{\min} = -\mathrm{fov}/2$. Для полного оборота $\Delta\alpha = 2\pi/N$;
для неполного $\Delta\alpha = \mathrm{fov}/(N-1)$, так что крайние лучи идут по
границам сектора. Направления лучей в СК робота вычисляются один раз; в каждом
скане они поворачиваются на курс (четыре умножения на луч вместо двух вызовов
тригонометрии).

**Трассировка по сетке.** Используется алгоритм Аманатидеса — Ву [3]: луч
$\mathbf p(t) = \mathbf o + t\,\mathbf d$ в единицах клеток переходит из клетки в
клетку, каждый раз выбирая ближайшее пересечение с вертикальной или
горизонтальной границей:

$$
t_x^{\text{next}} = \frac{(i_x + [d_x > 0]) - o_x}{d_x},\qquad
t_x^{\text{next}} \mathrel{+}= \frac{1}{|d_x|}\ \text{после шага по } x
$$

(аналогично по $y$). Дальность до препятствия получается по точке пересечения
границы клетки — без погрешности дискретизации.

**Ускорение по полю расстояний.** Для каждой свободной клетки заранее
вычисляется расстояние Чебышёва $k$ до ближайшей занятой клетки (двухпроходное
преобразование, точное для этой метрики; край сетки считается занятым).

*Утверждение.* Из любой точки клетки с расстоянием $k$ луч может пройти
евклидово расстояние $k - 1$ клеток, не попав в занятую клетку.

*Доказательство.* При перемещении на евклидово расстояние $s$ каждая координата
точки меняется не более чем на $s$, поэтому индекс клетки по каждой оси меняется
не более чем на $\lceil s\rceil$. При $s = k - 1$ точка остаётся в клетке на
расстоянии Чебышёва не более $k-1 < k$ от исходной, а все такие клетки свободны
по определению $k$. ∎

Поэтому при $k \ge 2$ луч делает «прыжок» на $(k-1) - 10^{-6}$ клеток (запас
страхует от ошибок округления) и заново вычисляет параметры обхода; вблизи стен
алгоритм возвращается к точным шагам. Измеренный выигрыш относительно обычного
обхода: в 1.5 раза в лабиринте с проходами 1.2 м и в 3.4 раза на пустой арене
(78 нс на луч в лабиринте). Совпадение с перебором всех клеток и примитивов
проверено на 6400 случайных лучах (тест `raycast_matches_brute_force`,
расхождение менее $10^{-9}$ м).

**Аналитические и подвижные препятствия.** Прямоугольники проверяются методом
слоёв, круги — решением квадратного уравнения
$t = \mathbf m\cdot\mathbf d - \sqrt{(\mathbf m\cdot\mathbf d)^2 - (|\mathbf m|^2 - R_o^2)}$,
$\mathbf m = \mathbf c - \mathbf o$. Подвижный круг радиуса $R_o$ на расстоянии
$d$ закрывает на скане сектор полушириной $\arcsin(R_o/d)$; проверяются только
лучи этого сектора.

**Модель измерения.** Для луча с истинной дальностью $\rho < \rho_{\max}$:

$$
z = \operatorname{clamp}\Bigl(Q\bigl(\rho + (\sigma_0 + \sigma_1\rho)\,\varepsilon\bigr),\ \rho_{\min},\ \rho_{\max}\Bigr),
\qquad \varepsilon \sim \mathcal N(0, 1),
$$

где $Q$ — квантование с шагом `lidar.resolution`. С вероятностью
`lidar.dropout_prob` отражение теряется, и тогда, как и при отсутствии
препятствия в пределах дальности, $z = \rho_{\max}$. По умолчанию
$\sigma_0 = 1$ см, $\sigma_1 = 0$, шаг квантования 1 мм. Тест
`lidar_noise_statistics` проверяет нулевое среднее, заданное СКО и долю потерь.

### 4.2. Инерциальный модуль

Акселерометр измеряет кажущееся ускорение в связанной СК
$\mathbf f_B = \dot{\mathbf v}_B + \omega\,\mathbf J\,\mathbf v_B$, где
$\mathbf J\mathbf v = (-v_y, v_x)^{\mathsf T}$ (в установившемся повороте
$\mathbf f_B = (0, \omega v_x)$ — центростремительное ускорение). Сенсор
опрашивается раз в период управления $T$ и выдаёт среднее за интервал
(предынтегрированное измерение):

$$
\bar{\mathbf f} = \frac{\mathbf v_B(T) - \mathbf v_B(0)}{T} + \frac{1}{T}\sum_{k}\omega_k\,\mathbf J\,\mathbf v_{B,k}\,\Delta t,
\qquad
\bar\omega = \frac{1}{T}\sum_k \omega_k\,\Delta t .
$$

Шум задан спектральными плотностями, поэтому его статистика не зависит от
периода опроса:

$$
z = \bar x + \beta + n,\qquad n \sim \mathcal N\bigl(0,\ N^2/T\bigr),\qquad
\beta_{k+1} = \beta_k + K_b\sqrt{T}\,\varepsilon_k,\qquad \beta_0 \sim \mathcal N(0, \sigma_{\beta 0}^2),
$$

где $N$ — плотность белого шума, $K_b$ — интенсивность случайного блуждания
смещения. По умолчанию для гироскопа $N = 2\cdot10^{-4}$ рад/с/√Гц (СКО отсчёта
$8.9\cdot10^{-4}$ рад/с при $T = 50$ мс), для акселерометра
$N = 2\cdot10^{-3}$ м/с²/√Гц.

### 4.3. Колёсная одометрия

Модель воспроизводит то, что делает прошивка робота, вместе с источниками её ошибок.

1. Энкодер. Приращение угла колеса за период получает случайную ошибку, дисперсия
   которой пропорциональна пройденному углу, и квантуется:
   $$\tilde\varphi \leftarrow \tilde\varphi + \Delta\varphi + k\sqrt{|\Delta\varphi|}\,\varepsilon,\qquad
   q = \Bigl\lfloor \tilde\varphi\,\frac{n}{2\pi} \Bigr\rfloor,\qquad
   \Delta\varphi^{\text{изм}} = \frac{2\pi}{n}\,\Delta q ,$$
   где $n$ — число тиков на оборот (4096). Дробный остаток не теряется: он
   остаётся в $\tilde\varphi$ до следующего шага.
2. Счисление пути. Прошивка «знает» радиусы колёс и колею с ошибками калибровки,
   постоянными в течение эпизода: $\hat r_i = r(1 + e_i)$, $\hat b = b(1 + e_b)$,
   $e_i \sim \mathcal N(0, 0.003^2)$, $e_b \sim \mathcal N(0, 0.005^2)$:
   $$\Delta s = \frac{\hat r_R\Delta\varphi_R + \hat r_L\Delta\varphi_L}{2},\qquad
   \Delta\theta = \frac{\hat r_R\Delta\varphi_R - \hat r_L\Delta\varphi_L}{\hat b},$$
   $$x \leftarrow x + \Delta s\cos\bigl(\theta + \tfrac{\Delta\theta}{2}\bigr),\quad
   y \leftarrow y + \Delta s\sin\bigl(\theta + \tfrac{\Delta\theta}{2}\bigr),\quad
   \theta \leftarrow \theta + \Delta\theta .$$

| Источник ошибки | Характер | Откуда берётся в модели |
| --- | --- | --- |
| Квантование энкодера | ограниченная, не копится | целочисленный счётчик тиков |
| Шум измерения угла | случайное блуждание | слагаемое $k\sqrt{\lvert\Delta\varphi\rvert}\,\varepsilon$ |
| Ошибка калибровки | систематический дрейф | $e_L$, $e_R$, $e_b$ на эпизод |
| Проскальзывание колёс | зависит от манёвра | из физики: угол колеса растёт, корпус стоит |

Без шумов счисление расходится с истиной менее чем на 2 мм за 20 с движения; с
параметрами по умолчанию дрейф в лабиринте составляет в среднем 18 см за эпизод
(раздел 10).

### 4.4. Наблюдения

Вектор `proprio` (float32, 15 компонент; индексы — `roversim.obs`):

| Индекс | Компонента | Источник |
| --- | --- | --- |
| 0–2 | угловая скорость, кажущиеся ускорения $x$, $y$ | IMU |
| 3–4 | скорости левого и правого колёс | энкодеры |
| 5–6 | линейная и угловая скорость | одометрия |
| 7–9 | счисленная поза $(x, y, \theta)$ | одометрия |
| 10–12 | расстояние до цели, косинус и синус её пеленга | истинная поза |
| 13–14 | косинус и синус пеленга точки маршрута (раздел 5) | истинные поза и карта |

Вектор `state` (float64, 12 компонент; индексы — `roversim.gt`) содержит истинное
состояние: позу, скорости корпуса и колёс, цель, среднюю силу давления стен,
оставшийся путь. Он предназначен для наград, метрик и отладки.

### 4.5. Генератор случайных чисел

Стандартные распределения C++ дают разные последовательности в разных
библиотеках, поэтому генератор реализован в проекте (`core/include/roversim/rng.hpp`):
xoshiro256++ [4] с развёрткой состояния через SplitMix64; равномерное число на
$[0,1)$ берётся из 53 старших бит; нормальное — полярным методом Марсальи
(из трансцендентных функций нужен только логарифм).

У каждого источника случайности свой поток, получаемый из seed эпизода и номера
потока: выбор старта и цели, шум лидара, IMU, одометрии, подвижные препятствия.
За одно измерение сенсор потребляет фиксированное количество случайных чисел, не
зависящее от сцены. Поэтому, например, изменение числа лучей лидара не сдвигает
шум IMU, а прогоны с разным управлением получают один и тот же шум — это
позволяет сравнивать алгоритмы попарно.

## 5. Задача навигации и награда

Реализация: `core/src/simulator.cpp`, `core/src/navgrid.cpp`.

**Эпизод.** При `reset(seed)` выбираются старт и цель. Клетка сетки проходима,
если круг радиуса $R$ плюс запас `task.spawn_clearance` с центром в её центре
свободен. Из 4-связных областей проходимых клеток оставляется наибольшая, и
обе точки берутся из неё — цель всегда достижима. Расстояние между ними — не
менее `task.min_goal_distance`.

**Кратчайшие пути.** От цели по проходимым клеткам распространяется волна
Дейкстры (8 соседей, диагональ длиной $\sqrt2$, без срезания углов). Вместо кучи
используются «корзины» шириной в одну клетку (алгоритм Дайела [5]): длина любого
ребра не меньше ширины корзины, поэтому релаксация из корзины $b$ попадает только
в корзины с большим номером, клетки текущей корзины окончательны, а сложность
линейна. Построение поля для лабиринта 144×144 клетки занимает 0.25 мс.

Расстояние $D(\mathbf p)$ от произвольной точки до цели — билинейная
интерполяция поля по центрам четырёх соседних клеток, поэтому оно меняется
непрерывно.

**Награда** за шаг управления:

$$
r_t = w_p\bigl(D(\mathbf p_{t-1}) - D(\mathbf p_t)\bigr) - c_{\text{step}}
- c_{\text{coll}}\,[\text{столкновение}] + r_{\text{goal}}\,[\text{цель достигнута}],
$$

по умолчанию $w_p = 1$ на метр, $c_{\text{step}} = 0.01$, $c_{\text{coll}} = 5$,
$r_{\text{goal}} = 10$. Слагаемое прогресса — потенциальная функция [6]: сумма по
эпизоду равна сокращению расстояния до цели и не меняет оптимальную политику, но
даёт плотный сигнал. В лабиринте принципиально, что $D$ — длина пути, а не
расстояние по прямой: прямая упирается в стену. Эпизод завершается при достижении
цели ($\lVert\mathbf p - \mathbf g\rVert < 0.3$ м), при столкновении (если
`task.terminate_on_collision`) и прерывается по лимиту шагов.

**Подсказка маршрута.** В наблюдение входит направление на точку кратчайшего
пути в `task.lookahead` метрах впереди. При построении поля для каждой клетки
запоминается следующая клетка на пути к цели; подсказка указывает на самую
дальнюю точку этого пути (в пределах $3\cdot$lookahead), видимую из положения
робота по прямой. Вдоль кратчайшего пути видимость пропадает один раз — за
углом, — поэтому граница находится двоичным поиском. Если цель видна, подсказка
смотрит прямо на неё. Так глобальный планировщик сообщает локальному, куда ехать;
для обучаемой политики это делает задачу марковской (раздел 9).

**Метрика SPL** (Success weighted by Path Length [7]) по $n$ эпизодам:

$$
\mathrm{SPL} = \frac1n\sum_{j=1}^{n} S_j\,\frac{\ell_j}{\max(\ell_j, p_j)},
$$

где $S_j \in \{0,1\}$ — успех, $\ell_j$ — длина кратчайшего пути от старта
(`Simulator::shortest_path_length`), $p_j$ — фактически пройденный путь.

## 6. Системный слой: буферы, IPC, биндинги

### 6.1. Буферы наблюдений и биндинги

Симулятор пишет наблюдения в три непрерывных буфера. Указатели на них либо
смотрят в собственную память объекта, либо заданы извне (`Simulator::Buffers`) —
так один и тот же код пишет в строку пакетного массива или прямо в сегмент
разделяемой памяти.

Python-модуль (`python/bindings.cpp`) отдаёт буферы как массивы NumPy,
созданные поверх памяти C++: массив не владеет данными (`owndata = False`),
ссылается на объект-владелец (`base`), удерживая его от удаления, и защищён от
записи. `torch.from_numpy` создаёт тензор поверх той же памяти. Таким образом от
ядра до тензора нет ни одного копирования; первая копия возникает там, где
она нужна по смыслу (нормировка признаков, буфер траекторий).

Обратная сторона — данные в таком массиве меняются при следующем шаге. Среда
`RoverEnv` по умолчанию возвращает копии (их ждут буферы воспроизведения и
стандартные обёртки), а режим без копирования включается явно.

На время `reset()` и `step()` блокировка интерпретатора (GIL) отпускается.

### 6.2. Пакетный симулятор

`VecSimulator` (`core/src/vec_simulator.cpp`) хранит $N$ независимых
симуляторов, которые пишут наблюдения в общие массивы $[N \times \text{dim}]$.
Шаг выполняется в пуле потоков: диапазон сред делится на равные непрерывные
куски, вызывающий поток берёт первый. Рабочие потоки перед засыпанием
кратковременно ждут активно — шаги следуют один за другим, и это убирает
задержку пробуждения, сравнимую с длительностью шага.

Среды не разделяют изменяемого состояния, а seed эпизода среды $i$ с номером $k$
равен $\operatorname{mix}(\operatorname{mix}(s + c\,(i+1)) + k)$, поэтому
результат не зависит от числа потоков (тест
`vec_simulator_is_independent_of_thread_count`). Статические данные — мир и
навигационная сетка — разделяются между средами. Завершившаяся среда
перезапускается в том же вызове; её наблюдение уже относится к новому эпизоду.

### 6.3. Разделяемая память

Реализация: `core/include/roversim/shm.hpp`, `core/src/shm.cpp`.

Сегмент POSIX (`shm_open`) состоит из заголовка и трёх блоков данных, выровненных
на 64 байта. Заголовок содержит только типы фиксированной ширины.

| Смещение | Поле | Тип | Кто пишет |
| --- | --- | --- | --- |
| 0 | `magic` («RSIM»; записывается последним — признак готовности) | u32 | сервер |
| 4, 8, 16 | `version`, `total_bytes`, `server_pid` | u32, u64, i64 | сервер |
| 24–32 | `num_rays`, `proprio_dim`, `state_dim` | u32 × 3 | сервер |
| 40–56 | смещения блоков `state`, `proprio`, `lidar` | u64 × 3 | сервер |
| 64–152 | период управления, геометрия лидара, размеры и кинематика робота | f64 × 12 | сервер |
| 192 | `cmd_seq` — номер команды (futex-слово) | atomic u32 | клиент |
| 196–256 | команда, флаги, seed, действие, старт, цель | u32, u64, f64 | клиент |
| 320 | `ack_seq` — номер выполненной команды (futex-слово) | atomic u32 | сервер |
| 324–352 | статус, награда, время, счётчики шагов и эпизодов | u32, f64, u64 | сервер |
| 360 | текст ошибки (96 байт) | char[] | сервер |
| 512 | `state_seq` — счётчик seqlock | atomic u32 | сервер |
| 576… | блоки: `state` f64[12], `proprio` f32[15], `lidar` f32[num_rays] | | сервер |

Поля, которые пишут разные процессы, лежат в разных линиях кэша.

**Протокол «запрос — ответ».**

```
клиент                                        сервер
записать команду и действие
cmd_seq ← cmd_seq + 1; futex_wake   ───────►  проснуться, выполнить reset/step
                                              (симулятор пишет наблюдения прямо в сегмент)
проснуться                          ◄───────  ack_seq ← cmd_seq; futex_wake
читать наблюдения по указателю
```

Обе стороны сначала ждут активно (по умолчанию до 200 мкс) и только потом
засыпают на futex: при непрерывном обмене партнёр почти всегда успевает ответить
за время спина, и системных вызовов ожидания нет. Время активного ожидания
настраивается (`ShmServer::set_spin_time`, `ShmClient::set_spin_time`, флаг
сервера `--spin-us`). Запись счётчика выполняется с порядком `release`,
чтение — `acquire`, поэтому данные команды и ответа видны другой стороне
полностью. Поскольку обмен строго поочерёдный, читатель и писатель наблюдений
никогда не работают одновременно.

**Сторонние наблюдатели** (журналирование, визуализация) подключаются в режиме
«только чтение» и получают согласованные снимки через seqlock: сервер делает
счётчик `state_seq` нечётным перед записью и чётным после; читатель копирует
данные и повторяет попытку, если счётчик был нечётным или изменился.

**Отказы.** Сегмент, оставшийся от аварийно завершившегося сервера, заменяется
(проверяется, жив ли процесс с записанным PID). Некорректная команда (например,
старт внутри стены) не роняет сервер: клиент получает исключение с текстом
ошибки. При остановке сервера `magic` обнуляется, и ожидающий клиент получает
исключение вместо зависания.

**Измерения.** Стоимость транспорта измеряется парно: для каждого шага берётся
время запроса у клиента и время, которое сервер потратил на сам шаг (он сообщает
его через `ShmServer::last_command_seconds`); их разность — публикация команды,
пробуждение сервера, публикация ответа и пробуждение клиента. Сравнивать медианы
двух отдельных прогонов (через сегмент и в одном процессе) нельзя: искомая
величина на два порядка меньше шага симуляции и тонет в дрейфе частоты
процессора — такая оценка давала от −6 до +2 мкс.

| Режим обмена (360 лучей, шаг ≈ 45 мкс) | Задержка запроса, медиана | Транспорт, медиана | Транспорт, 99 % |
| --- | --- | --- | --- |
| Запросы подряд: обе стороны в активном ожидании | 45 мкс | 0.5 мкс | 1–6 мкс |
| Клиент занят 1 мс между запросами: сервер спит на futex | 100 мкс | 40–48 мкс | 160–290 мкс |
| То же, время активного ожидания сервера 5 мс | 48 мкс | 0.6 мкс | 20–180 мкс |

Диапазоны — разброс между шестью запусками `roversim_bench`; медианы устойчивы, а
99-й процентиль определяется вытеснением потоков на общей виртуальной машине.

Половина микросекунды — это два системных вызова `futex_wake` без ожидающих
(по 0.18 мкс на той же машине) и переход двух линий кэша между ядрами. Во втором
режиме к ним добавляется пробуждение спящего потока планировщиком ОС, а сам шаг
после сна идёт медленнее (55 мкс вместо 45 — по-видимому, из-за остывшего кэша).
Отсюда практическое правило: если клиент между шагами считает дольше времени
активного ожидания, а задержка важна, это время нужно увеличить — ценой ядра,
занятого ожиданием. Результаты обмена побитно совпадают с симуляцией в процессе
(тест `shared_memory_matches_in_process_simulation`).

### 6.4. Визуализация

Визуализация отделена от симуляции: без её вызовов ядро работает в
headless-режиме.

* `viz::Renderer` — программный растеризатор вида сверху; кадр RGB используется
  как `rgb_array` в Gymnasium и выводится в терминал цветными полублоками
  (`viz::to_ansi`).
* `viz::WebViewer` — встроенный HTTP/WebSocket-сервер (RFC 6455; SHA-1 и Base64
  для рукопожатия реализованы в проекте). Один фоновый поток обслуживает
  соединения через `poll()`. Поток симуляции только кладёт готовый бинарный кадр
  в общий слот, рассылкой занимается сервер, поэтому медленный браузер не
  тормозит симуляцию. Если зрителей нет, вызов `publish()` стоит десятки
  наносекунд. Браузер может отправлять команды ручного управления.

### 6.5. Детерминизм

Гарантия: при одинаковых конфигурации, мире, seed и последовательности действий
траектория и показания сенсоров совпадают бит в бит. Она обеспечивается так:

* фиксированный шаг по времени; симулятор не обращается к часам;
* собственный генератор случайных чисел и распределения (раздел 4.5);
* флаг `-ffp-contract=off` запрещает слияние $a\cdot b + c$ в одну операцию FMA,
  иначе результат зависел бы от набора инструкций процессора; `-ffast-math` не
  используется;
* приведение угла к $[-\pi, \pi]$ через `std::remainder` и корень через `sqrt` —
  точные по IEEE-754 операции;
* в пакетном режиме среды не разделяют изменяемого состояния.

Проверяется тестами: повторный прогон (`simulation_is_deterministic`), пакет сред
при разном числе потоков, обмен через разделяемую память, прогон с подвижными
препятствиями. Между платформами возможны расхождения в последнем разряде из-за
реализаций `sin`, `cos`, `log` в libm.

## 7. SLAM: карта занятости и локализация

Реализация: `core/src/nav/occupancy_grid.cpp`, `core/src/nav/slam.cpp`.

### 7.1. Карта занятости

Карта — сетка клеток $m_j$, для каждой оценивается вероятность занятости
$p(m_j \mid z_{1:t}, x_{1:t})$ по сканам $z$ из известных поз $x$. При обычных
допущениях (клетки независимы, наблюдения условно независимы) байесовское
обновление в лог-шансах $l = \ln\frac{p}{1-p}$ сводится к сложению [8]:

$$
l_t(m_j) = l_{t-1}(m_j) + \ln\frac{p(m_j \mid z_t, x_t)}{1 - p(m_j \mid z_t, x_t)} - l_0 ,
$$

где $l_0 = 0$ (априорная вероятность 0.5). Обратная модель сенсора для лидара:

$$
\Delta l(m_j) =
\begin{cases}
+\,l_{\text{hit}} = 0.85 & \text{луч закончился в клетке } (p \approx 0.70),\\
-\,l_{\text{miss}} = 0.40 & \text{луч прошёл через клетку } (p \approx 0.40),\\
0 & \text{клетка лучом не затронута.}
\end{cases}
$$

Значения ограничены отрезком $[l_{\min}, l_{\max}] = [-2.0,\ 3.5]$. Ограничение не
даёт карте стать «самоуверенной» и позволяет ей забывать: клетка, откуда ушёл
объект, освобождается за несколько сканов. Клетка считается занятой при $l > 0.6$
($p > 0.65$), свободной при $l < -0.6$, иначе — неразведанной.

За один скан каждая клетка обновляется не более одного раза, причём «занято»
имеет приоритет над «свободно»: сначала отмечаются клетки отражений, затем
трассируется свободное пространство, пропуская уже отмеченные клетки. Это
соответствует допущению о независимости сканов, а не отдельных лучей.

**Память попаданий.** Два вида наблюдений неравноценны. Отражение — прямое
свидетельство препятствия. Вывод «луч прошёл сквозь клетку» — косвенное: он
верен лишь с точностью до ошибки позы, а она (≈ 2 см) сравнима с половиной
клетки. Хуже всего приходится стене, вдоль грани которой идут лучи: когда робот
огибает её торец, лучи скользят по грани почти вплотную, трассировка проходит по
клеткам самой стены, и за полсекунды (десяток сканов) стена исчезает с карты.
Планировщик прокладывает маршрут «сквозь» неё, робот едет туда, видит стену
заново, возвращается — и так по кругу, пока не истечёт время эпизода.

Поэтому клетка помнит до 200 попаданий, и наблюдение «свободно» сначала гасит
одно из них и лишь затем начинает снижать оценку:

$$
\text{«свободно»:}\quad
\begin{cases}
h \leftarrow h - 1, & h > 0,\\
l \leftarrow \max(l - l_{\text{miss}},\ l_{\min}), & h = 0,
\end{cases}
\qquad
\text{«занято»:}\quad h \leftarrow \min(h + 1,\ 200)\ \text{при } l = l_{\max}.
$$

Запоминаются только попадания, подтверждающие уже уверенно занятую клетку
($l = l_{\max}$). У стены таких сотни; у объекта, проезжающего через клетку за
несколько сканов, их нет, и его след на карте стирается так же быстро, как
раньше. Забывание сохраняется, но его время пропорционально тому, как долго
клетка наблюдалась занятой (не более 10 с непрерывных наблюдений «свободно»).
Измеренный эффект (раздел 10.2): доля ошибочно свободных клеток стен падает с
2.8 % до 1.6 %, а число эпизодов, в которых робот не дошёл до цели, в трёх
конфигурациях стека — с 7 из 600 до 2 из 600.

### 7.2. Алгоритм Брезенхема

Клетки вдоль луча перечисляет алгоритм Брезенхема [9]. Его идея — двигаться по
одной клетке вдоль «длинной» оси и накапливать в целочисленной переменной
отклонение идеальной линии по «короткой» оси; когда накопилась целая клетка,
делается шаг и по ней. В классическом виде для отрезка между центрами клеток
$(x_0, y_0) \to (x_1, y_1)$ при $\Delta x \ge \Delta y \ge 0$:

```
err ← 2·Δy − Δx
для x от x0 до x1:
    отметить (x, y)
    если err > 0:  y ← y + 1;  err ← err − 2·Δx
    err ← err + 2·Δy
```

В проекте используется вариант с **точной инициализацией ошибки**. Концы луча
заданы не центрами клеток, а реальными координатами, которые хранятся в
фиксированной точке с шагом $1/256$ клетки: $(X_0, Y_0)$, $(X_1, Y_1)$. Для
столбца с центром $x_c$ ордината линии равна

$$
y(x_c) = Y_0 + \frac{\Delta Y}{|\Delta X|}\,|x_c - X_0| = \frac{A}{|\Delta X|},\qquad
A = Y_0\,|\Delta X| + \Delta Y\,|x_c - X_0| .
$$

Строка клетки — $\lfloor A / (256\,|\Delta X|) \rfloor$, остаток от деления и есть
накопитель ошибки. При переходе к следующему столбцу $A$ увеличивается на
$256\,\Delta Y$, и поскольку $|\Delta Y| \le |\Delta X|$, строка меняется не более
чем на единицу — та же целочисленная схема «прибавить и сравнить», что у
классического алгоритма, но линия проходит по клеткам, в которых луч
действительно находится в середине каждого столбца. Тест
`occupancy_grid_traces_rays_with_bresenham` проверяет набор клеток для
горизонтального и диагонального лучей.

### 7.3. Учёт угла падения

Луч, идущий почти вдоль стены, на последних метрах находится от неё в
сантиметрах. Оценка позы имеет погрешность того же порядка (сантиметры, доли
градуса), поэтому такой луч при построении карты легко «промахивается» и
рисуется по клеткам самой стены, помечая их свободными.

Поэтому свободным помечается только участок луча, удалённый от поверхности
больше чем на $c = 1.5$ клетки: хвост длиной $c/\sin\gamma$ пропускается, где
$\gamma$ — угол между лучом и поверхностью. Касательная к поверхности оценивается
по соседним точкам скана, если их дальности близки:

$$
\sin\gamma_i = \frac{\lvert \mathbf d_i \times (\mathbf p_{i+1} - \mathbf p_{i-1})\rvert}{\lVert \mathbf p_{i+1} - \mathbf p_{i-1}\rVert}.
$$

Для луча по нормали пропускаются полторы клетки перед стеной, для скользящего под
углом 10° — около девяти.

Эффект измеряется так: после эпизода для каждой истинной клетки поверхности
стены, которую робот наблюдал, проверяется состояние клетки карты, содержащей её
центр. В 200 эпизодах навигации (158 тыс. таких клеток) без поправки
(`surface_clearance = 0`) свободными оказываются 3.4 % клеток стен, с поправкой —
1.6 % (без памяти попаданий — 6.5 % и 2.8 %). Оставшаяся доля — в основном не
стирание стен, а сдвиг карты на величину ошибки позы (2 см при клетке 5 см):
центр клетки стены лежит всего в 2.5 см за её поверхностью. На исход навигации
поправка влияет слабо: без неё цели достигнуты в 198 эпизодах из 200 вместо 200,
а маршрут перестраивается на 9 % чаще.

### 7.4. Сопоставление скана с картой

Одометрия дрейфует, и карта, построенная только по ней, искажается. Поэтому поза
уточняется сопоставлением текущего скана с уже построенной картой
(scan-to-map matching). Пусть $M(\mathbf q) \in [-1, 1]$ — значение карты в
точке, полученное билинейной интерполяцией по центрам клеток
($+1$ — уверенно занято, $-1$ — уверенно свободно, $0$ — не разведано), а
$\mathbf p_i$ — точки скана в СК робота. Максимизируется

$$
J(\boldsymbol\xi) = \frac1n\sum_{i=1}^{n} M\bigl(\mathbf T(\boldsymbol\xi)\,\mathbf p_i\bigr)
- k_t\,\lVert \mathbf t - \mathbf t_0\rVert^2 - k_r\,(\theta - \theta_0)^2,
\qquad \boldsymbol\xi = (\mathbf t, \theta),
$$

где $\boldsymbol\xi_0$ — прогноз по одометрии. Первое слагаемое велико, когда точки
скана ложатся на занятые клетки, и отрицательно, если они попадают в заведомо
свободное место. Второе и третье — априорное распределение вокруг прогноза
($k_t = 30$ м⁻², $k_r = 60$ рад⁻²): оно удерживает решение там, где геометрия его
не определяет, — например, вдоль длинного коридора, где сдвиг скана вдоль стен не
меняет первое слагаемое.

Поиск — покоординатный подъём с дроблением шага (как в GMapping [10]): из текущей
позы пробуются шесть соседних ($\pm$шаг по $x$, по $y$ и по углу), выбирается
лучшая; когда улучшения нет, шаг делится пополам. Начальные шаги 2 см и 0.01 рад,
четыре уровня — конечное разрешение 2.5 мм и 0.07°. Используется 120 лучей скана;
время сопоставления около 0.1 мс.

Результат принимается, если средняя «занятость» под точками скана не меньше 0.25;
иначе (мало общего с картой) поза берётся из прогноза. Первые пять сканов только
строят карту.

### 7.5. Цикл SLAM

На каждый скан `GridSlam` выполняет:

1. **Прогноз.** Приращение одометрии между сканами, выраженное в прошлой СК
   робота, применяется к прошлой оценке:
   $\boldsymbol\xi_0 = \boldsymbol\xi_{t-1} \oplus \bigl(\ominus\,\mathbf o_{t-1} \oplus \mathbf o_t\bigr)$.
   Используется только приращение, поэтому накопленный дрейф одометрии не важен.
2. **Коррекция** — сопоставление скана с картой (раздел 7.4).
3. **Картографирование** — встраивание скана в карту из уточнённой позы
   (разделы 7.1–7.3). Лучи, попавшие в подвижные объекты, занятыми клетки не
   помечают (раздел 8.4).

Это «фронтенд» SLAM: замыкания циклов нет. Ошибка накапливается только при
освоении новых областей; в уже снятой местности поза привязана к карте.

**Результат.** В 200 эпизодах навигации по неизвестным лабиринтам средняя ошибка
положения в конце эпизода — 2.2 см у SLAM против 18.8 см у чистой одометрии. Без
сопоставления сканов (карта по одной одометрии) ошибка составляет 18.9 см, а доля
достигнутых целей падает с 200/200 до 156/200: искажённая карта перекрывает
проходы (в ней 19 % клеток стен помечены свободными, а стены, «переехавшие»
вместе с дрейфом, принимаются трекером за подвижные объекты на 27 % тактов).

## 8. Планирование движения

Реализация: `core/src/nav/planner.cpp`, `tracker.cpp`, `dwa.cpp`, `navigator.cpp`.

### 8.1. Карта стоимости

По карте занятости строится расстояние от каждой клетки до ближайшей занятой —
точное евклидово преобразование расстояний Фельценсвальба — Хуттенлохера [11].
Оно раскладывается на одномерные задачи $D(q) = \min_p\bigl((q-p)^2 + f(p)\bigr)$,
каждая из которых решается построением нижней огибающей парабол за линейное
время: сначала по столбцам, затем по строкам. Совпадение с перебором проверяет
тест `distance_transform_is_exact`.

Пусть $c$ — расстояние от клетки до границы ближайшей занятой клетки. Множитель
стоимости движения:

$$
w(c) =
\begin{cases}
\infty\ (\text{клетка запрещена}) & c < r_{\text{let}} = R + 0.06\ \text{м},\\[1mm]
1 + w_s\Bigl(\dfrac{r_s - c}{r_s - r_{\text{let}}}\Bigr)^{2} & r_{\text{let}} \le c < r_s = 0.5\ \text{м},\\[2mm]
1 & c \ge r_s,
\end{cases}
\qquad w_s = 4 .
$$

Запретная зона гарантирует, что корпус не заденет стену; «мягкая» зона
удерживает маршрут в середине проходов. Неразведанные клетки проходимы с
добавкой 0.5 к множителю (оптимистичное планирование): робот едет к цели через
неизвестное и перепланирует, когда лидар открывает новые стены. Карта стоимости
строится только по окну, охватывающему разведанную область, старт и цель.

### 8.2. A*

Поиск по 8-связной сетке минимизирует $f(n) = g(n) + h(n)$, где $g$ — стоимость
пути от старта, $h$ — оценка остатка. Стоимость перехода между соседними клетками
равна его длине, умноженной на среднее множителей $w$ этих клеток. Эвристика —
октильное расстояние

$$
h(n) = \bigl(\max(\Delta x, \Delta y) + (\sqrt2 - 1)\min(\Delta x, \Delta y)\bigr)\,\delta ,
$$

где $\delta$ — размер клетки. Она допустима и монотонна (множитель стоимости не
меньше единицы), поэтому A* находит оптимальный по стоимости путь и не раскрывает
клетки повторно. Диагональный переход запрещён, если запрещена хотя бы одна из
двух клеток, которые он «срезает».

### 8.3. Theta*

Путь A* привязан к восьми направлениям и получается «лесенкой». Theta* [12]
строит путь под любым углом: родителем клетки может быть любая клетка в прямой
видимости. При релаксации соседа $s'$ вершины $s$ с родителем $p$:

$$
g(s') \leftarrow \min\bigl(g(s'),\ g(p) + c(p, s')\bigr)\ \text{если } s' \text{ виден из } p;
\qquad \text{иначе}\quad g(s') \leftarrow \min\bigl(g(s'),\ g(s) + c(s, s')\bigr).
$$

Видимость проверяется линией Брезенхема по запретным клеткам; одновременно вдоль
линии накапливается средний множитель стоимости, так что прямой переход учитывает
близость стен так же, как сеточные шаги:
$c(p, s') = \lVert p - s'\rVert\cdot\overline{w}$. Эвристика — расстояние по
прямой.

Сравнение (тест `planners_find_short_safe_paths`): путь Theta* не длиннее
сеточного пути A* и состоит из меньшего числа отрезков; оба нигде не подходят к
стенам ближе радиуса робота. В задаче навигации (раздел 10) оба варианта —
Theta* и A* с последующим спрямлением — приводят робота к цели во всех 200
эпизодах, а различие в SPL (0.938 и 0.948) лежит в пределах статистического
разброса: стандартная ошибка SPL на 200 эпизодах около 0.01. Различается время
поиска: 3.2 мс против 0.7 мс на одних и тех же картах стоимости (3900 и 3100
раскрытых вершин; у Theta* на каждую вершину приходится ещё и проверка
видимости). При перепланировании раз в полторы секунды это 0.1 мс на такт
управления, поэтому по умолчанию оставлен Theta*: он строит путь с учётом
стоимости за один проход, тогда как спрямление после A* стоимость не учитывает.

### 8.4. Сопровождение подвижных объектов

Чтобы разойтись с движущимся препятствием, нужна его скорость. Трекер
(`ObstacleTracker`) получает её из сканов в три шага.

**Обнаружение сравнением с картой.** Карта запоминает для каждой клетки, сколько
раз та наблюдалась свободной. Клетка, подтверждённая не менее трёх раз, — «пол».
Отражение лидара считается принадлежащим подвижному объекту, если оно пришло с
пола: полом являются и клетка отражения, и все восемь её соседей.

Обе детали существенны. Проверка соседей исключает стены: рядом со стеной всегда
есть клетки, свободными не бывавшие, поэтому шум дальности и погрешность позы,
сдвигающие отражение от стены на соседнюю клетку, ложных срабатываний не дают.
Использование памяти, а не текущего состояния клетки, нужно для объектов,
движущихся на сенсор: такой объект успевает пометить клетки перед собой
занятыми, но полом они от этого быть не перестают. Первая версия, опиравшаяся на
текущее состояние, сопровождала надвигающееся препятствие лишь в 5 % случаев; с
памятью — в 100 %.

**Сегментация.** Соседние лучи-кандидаты с разностью дальностей не более 0.25 м
объединяются в сегмент. Сегмент описывается кругом: радиус — половина хорды
между крайними точками, центр — на луче через середину сегмента на расстоянии
$\rho_{\min} + R_{\text{obj}}$.

**Сопровождение.** Измерения привязываются к трекам по ближайшему прогнозу в
пределах 0.5 м. Состояние трека обновляет альфа-бета фильтр — стационарный фильтр
Калмана для модели постоянной скорости:

$$
\hat{\mathbf p}^{-} = \hat{\mathbf p} + \hat{\mathbf u}\,T,\qquad
\boldsymbol\nu = \mathbf z - \hat{\mathbf p}^{-},\qquad
\hat{\mathbf p} = \hat{\mathbf p}^{-} + \alpha\,\boldsymbol\nu,\qquad
\hat{\mathbf u} \leftarrow \hat{\mathbf u} + \frac{\beta}{T}\,\boldsymbol\nu .
$$

Коэффициенты связаны условием критического демпфирования
$\beta = \alpha^2/(2-\alpha)$; значения $\alpha = 0.35$, $\beta = 0.075$ выбраны
по замерам как компромисс между шумом оценки (центр круга определяется с
точностью до шага лучей) и запаздыванием после отскока препятствия.

**Подвижный или просто новый.** Отражение с пола означает «здесь что-то
появилось», но ещё не «это движется». В статичном мире такие отражения тоже
встречаются. Их источник — торцы стен: стена толщиной 0.2 м, обрывающаяся в
проходе, имеет торец шириной всего в четыре клетки, и лучи, проходящие вплотную
мимо него к дальним стенам, при сантиметровой ошибке позы задевают его клетки.
Если карта успела «стереть» торец, при взгляде в упор он выглядит предметом,
появившимся на полу. Состояния трека:

* лучи трека не помечают клетки карты занятыми (отметка `Dynamic`), пока он не
  признан неподвижным;
* **подвижным** трек считается со второго наблюдения — такие треки передаются в
  DWA с прогнозом движения;
* трек, 2.5 с не покидавший окрестность 0.15 м, признаётся **неподвижным**
  («припаркованным»): его лучи заносятся в карту с отметкой `Settled`, которая
  заодно стирает память «пола» в клетках отражения, поэтому повторно объект не
  обнаруживается.

Следствие такой схемы — редкие ложные подвижные объекты: стёртый торец стены до
«парковки» числится подвижным. В статичных лабиринтах ложный объект присутствует
на 0.03 % тактов (без памяти попаданий, раздел 7.1, — на 0.19 %).

Их можно исключить совсем: параметр `tracker.confirm_travel` требует, чтобы
оценка положения сначала ушла от места первого обнаружения на заданное
расстояние. При 0.15 м ложных объектов в статичных лабиринтах нет, а при
искажённой карте (без сопоставления сканов) их доля падает с 27 % до 13 % тактов.
Цена — задержка в признании настоящих препятствий на 0.3–0.75 с (путь 0.15 м при
скоростях 0.5–0.2 м/с). На 800 эпизодах с подвижными препятствиями выигрыша
правило не дало: без касаний прошли 670 эпизодов против 678 без него, а касаний
в первые секунды эпизода стало 7 вместо 5 (раздел 10.2). Различие лежит в
пределах статистического разброса, но и оно не в пользу правила, поэтому по
умолчанию оно выключено: быстрая реакция на настоящее препятствие важнее
редкого ложного объекта у торца стены.

**Точность.** Для неподвижного робота (пустая арена 7 × 7 м, два препятствия)
средняя ошибка оценки скорости — 0.06 м/с, положения — 6 см; подвижными
препятствия числятся 86 % времени — в остальное объект ещё не захвачен, заслонён
либо находится у самой стены, где его отражения не лежат на «полу». В
навигационных прогонах, где движется и сам робот, ошибка скорости —
0.10–0.12 м/с при скоростях препятствий 0.2–0.5 м/с.

### 8.5. Метод динамического окна

Локальный планировщик — метод динамического окна (DWA) [13], расширенный
прогнозом движения препятствий. На каждом такте:

**1. Динамическое окно.** Скорости, достижимые из текущих $(v, \omega)$ за время
$T_w = 0.2$ с при ограниченных ускорениях, пересекаются с допустимыми для робота:

$$
V_d = \bigl\{(v', \omega') : |v' - v| \le a_{\max}T_w,\ |\omega' - \omega| \le \varepsilon_{\max}T_w\bigr\}
\cap \bigl\{0 \le v' \le v_{\lim},\ |\omega'| \le \omega_{\lim}\bigr\}.
$$

Окно дискретизуется сеткой $9 \times 21$.

**2. Моделирование.** Для каждой пары $(v', \omega')$ строится дуга на горизонт
$T_h = 1.6$ с шагом 0.1 с (формулы раздела 3.1). В каждой точке
$\mathbf q_k = \mathbf q(t_k)$ вычисляется зазор до препятствий:

$$
c_k = \min\Bigl(D_{\text{loc}}(\mathbf q_k) - R,\ \ \min_j\ \bigl\lVert \mathbf q_k - (\mathbf o_j + \mathbf u_j t_k)\bigr\rVert - R_j - R - \delta_m\Bigr).
$$

Первый член — статические препятствия: $D_{\text{loc}}$ — евклидово поле
расстояний до точек текущего скана на локальной сетке $\pm 2$ м (одно чтение
таблицы вместо перебора точек скана). Второй — подвижные объекты из трекера,
сдвинутые на время $t_k$ со своей скоростью $\mathbf u_j$; $\delta_m = 0.1$ м —
запас на неточность прогноза. Точки скана, лежащие на самом сопровождаемом
объекте (ближе $R_j + \delta_m$ к его центру), в статическое поле не входят:
объект уже учтён вторым членом.

**3. Допустимость.** Если на шаге $k_c$ зазор впервые становится меньше порога,
траектория допустима, только когда робот успевает остановиться раньше:
$v'^2/(2a_{\max}) \le v'\,t_{k_c - 1}$. Порог равен запасу безопасности 5 см; если
робот уже оказался ближе, порогом становится текущий зазор — стоять, поворачиваться
и удаляться можно, приближаться нельзя.

Порогов два: зазор до статических препятствий и зазор до подвижных проверяются
каждый со своим. Это не формальность. С общим порогом робот, которого коснулось
подвижное препятствие (текущий зазор — ноль), терял запас сразу до всего: любая
траектория с неотрицательным зазором становилась допустимой, и, отъезжая от
препятствия, робот мог упереться в стену — такие касания стен наблюдались в
эксперименте. С раздельными порогами близость к подвижному объекту запас до
стен не отменяет (тест `dwa_keeps_wall_margin_when_touched_by_moving_obstacle`).

**4. Выбор.** Среди допустимых максимизируется

$$
G = w_g\,\frac{d_{\max} - d}{d_{\max} - d_{\min}}
  + w_h\Bigl(1 - \frac{|\Delta\psi|}{\pi}\Bigr)
  + w_c\,\frac{\min(c, c_{\text{cap}})}{c_{\text{cap}}}
  + w_v\,\frac{v'}{v_{\lim}}
  + w_s\,\frac{t_c}{T_h},
$$

где $d$ — расстояние от конца траектории до локальной цели (нормировано по
множеству допустимых траекторий, как в исходной работе), $\Delta\psi$ — ошибка
курса на цель в конце траектории, $c$ — минимальный зазор, $t_c$ — время до
первого прогнозируемого столкновения ($T_h$, если его нет). Веса:
$w_g = 1$, $w_h = 0.3$, $w_c = 0.25$, $w_v = 0.15$, $w_s = 1.5$.

Последнее слагаемое введено из-за подвижных препятствий. В классическом DWA
остановка всегда безопасна; от объекта, который сам едет на робота, она не
спасает, и из «плохих» вариантов нужно выбирать тот, где столкновение наступает
позже или не наступает вовсе. Когда подвижный объект рядом и приближается, окно
расширяется задним ходом (до $-0.5$ м/с). В обычном режиме задний ход запрещён:
эксперимент показал, что иначе при цели за спиной робот пятится к ней всю
дорогу, вместо того чтобы развернуться.

### 8.6. Навигатор

`Navigator` связывает компоненты в контур управления с периодом $T$:

1. SLAM: прогноз и коррекция позы.
2. Трекер: обнаружение и сопровождение подвижных объектов.
3. Картографирование (без лучей подвижных объектов).
4. Глобальный маршрут. Перепланирование событийное: не реже раза в 2 с (вдруг
   открылся путь короче), а также сразу, как только на ближайших 3 м маршрута в
   обновлённой карте появилось препятствие (но не чаще раза в 0.25 с). По
   сравнению с перепланированием по таймеру раз в 0.5 с число вызовов
   планировщика упало с 43 до 16 на эпизод при том же качестве.
5. Локальная цель — точка маршрута в 0.7 м впереди проекции робота на маршрут.
6. Если локальная цель сбоку или сзади (пеленг больше 1 рад) — разворот на
   месте; иначе DWA.
7. Восстановление: если за 2.5 с робот не продвинулся на 15 см — отъезд назад на
   1 с (или разворот, если сзади занято) и перепланирование. Если маршрута на
   текущей карте нет — ожидание с повторными попытками.

Навигатору нужны только скан лидара и одометрия; истинные поза и карта не
используются.

Карта имеет фиксированный размер (по умолчанию 20 × 20 м) с центром в точке
старта. Цель за её пределами недостижима в принципе, поэтому `set_goal` в этом
случае сообщает об ошибке, а не оставляет навигатор ждать маршрута.

Необязательная стартовая пауза (`startup_time`, по умолчанию 0) заставляет
навигатор после включения стоять и только наблюдать. Смысл в том, что в первую
секунду карты вокруг ещё нет и трекеру не с чем сравнивать скан: препятствие,
которое с самого старта едет навстречу, неотличимо от стены. Пауза в 1 с
сокращает число касаний в первые три секунды эпизода с 5 до 2 на 800 эпизодов,
но на общий результат не влияет (682 эпизода без касаний против 678), поэтому по
умолчанию она выключена.

## 9. Обучение с подкреплением

Реализация: `rl/model.py`, `rl/train_ppo.py`, `rl/evaluate.py`.

### 9.1. Постановка

Задача — марковский процесс принятия решений; эпизод — проезд от случайного
старта до случайной цели в случайном лабиринте.

**Наблюдение.** Скан лидара из 90 лучей (шаг 4°), обрезанный на 4 м и
нормированный на $[0, 1]$, и семь скалярных признаков: линейная и угловая
скорость по одометрии (в долях максимума), расстояние до цели, косинус и синус
пеленга цели, косинус и синус пеленга подсказки маршрута (раздел 5).

Подсказка принципиальна. В лабиринте направление на цель по прямой не говорит,
куда ехать, и без памяти задача не марковская. Подсказка — выход глобального
планировщика; политика выступает обучаемым локальным планировщиком, то есть
заменой DWA, а не всего навигационного стека.

**Действие** $\mathbf a \in [-1, 1]^2$ преобразуется в команду скоростей:
$v = \tfrac12(a_1 + 1)\,v_{\max}$ (только вперёд), $\omega = 0.45\,a_2\,\Omega_{\max}$.

**Награда** — по формуле раздела 5, умноженная на 0.2 для масштаба функции
ценности. Эпизод завершается при достижении цели или столкновении и прерывается
через 600 шагов (30 с).

### 9.2. Алгоритм

Используется PPO [14] с обобщённой оценкой преимущества (GAE) [15]. Преимущество
вычисляется по собранной траектории рекуррентно:

$$
\delta_t = r_t + \gamma V(s_{t+1}) - V(s_t),\qquad
\hat A_t = \delta_t + \gamma\lambda\,\hat A_{t+1},
$$

причём на границе эпизода цепочка обрывается. Политика обновляется по отсечённой
суррогатной цели

$$
L^{\text{clip}}(\vartheta) = \mathbb E_t\Bigl[\min\bigl(\rho_t\hat A_t,\ \operatorname{clip}(\rho_t,\,1-\epsilon,\,1+\epsilon)\,\hat A_t\bigr)\Bigr],
\qquad \rho_t = \frac{\pi_\vartheta(a_t \mid s_t)}{\pi_{\vartheta_{\text{old}}}(a_t \mid s_t)},
$$

а полная функция потерь равна

$$
L = -L^{\text{clip}} + c_v\,\tfrac12\,\mathbb E_t\bigl[(V_\vartheta(s_t) - \hat R_t)^2\bigr] - c_e\,\mathbb E_t\bigl[\mathcal H(\pi_\vartheta(\cdot \mid s_t))\bigr],
\qquad \hat R_t = \hat A_t + V(s_t).
$$

| Гиперпараметр | Значение |
| --- | --- |
| Параллельных сред × шагов на обновление | 256 × 64 = 16 384 перехода |
| Проходов по данным, мини-пакетов | 4, 8 (по 2048) |
| Оптимизатор, скорость обучения | Adam, $3\cdot10^{-4}$, линейно убывает до нуля |
| $\gamma$, $\lambda$, $\epsilon$ | 0.99, 0.95, 0.2 |
| $c_v$, $c_e$, ограничение нормы градиента | 0.5, 0.003, 0.5 |
| Обучающих лабиринтов | 64 (5 × 5 ячеек, проходы 1.2 м, 15 % пробитых стен) |

**Сеть.** Скан — кольцевой сигнал (последний луч соседствует с первым), поэтому
его обрабатывают одномерные свёртки с циклическим дополнением: 1→16 каналов
(ядро 5, шаг 2), 16→32 (ядро 5, шаг 2), 32→32 (ядро 3, шаг 2), ReLU. Выход
(384 признака) объединяется с семью скалярами и проходит два полносвязных слоя
по 128 нейронов (tanh). Из общего представления выходят среднее гауссовой
политики (2 значения) и оценка ценности; логарифм СКО — обучаемый параметр, не
зависящий от состояния. Всего 72 869 параметров.

**Поток данных.** Среды шагают в потоках ядра; наблюдения попадают в PyTorch без
копирования (раздел 6.1). Скорость обучения — около 7.4 тыс. шагов среды в
секунду на четырёх ядрах, из них большую часть времени занимает обновление сети
на CPU.

**Отбор модели.** Наборы лабиринтов не пересекаются: 64 обучающих (seed
генератора 0…63), 32 проверочных (от 1 000 000) и 64 тестовых (от 3 000 000).
Каждые 20 обновлений детерминированная политика проходит 300 эпизодов на
проверочных лабиринтах; в файл записываются веса с лучшей долей успеха. Итоговые
метрики считаются на тестовом наборе, который в отборе не участвовал.

| `ppo_rover.pt` | статичные лабиринты | 99.9 % | 0.0 % | 0.1 % | 0.998 |
| `ppo_rover.pt` | + 2 подвижных препятствия (в обучении не было) | 71.6 % | 28.3 % | 0.1 % | 0.715 |
| `ppo_rover_dynamic.pt` | + 2 подвижных препятствия (обучена с ними) | 78.9 % | 19.6 % | 1.5 % | 0.775 |
| `ppo_rover_dynamic.pt` | статичные лабиринты | 97.7 % | 0.0 % | 2.3 % | 0.961 |

Каждая из 64 сред отыгрывает одинаковое число эпизодов. Считать «первые
$N$ завершившихся» нельзя: эпизоды со столкновением короче успешных и попали бы
в выборку чаще, занижая долю успеха. Стандартная ошибка доли при 1000 эпизодах
не превышает 1.6 п. п.

Политика обобщается на новые лабиринты без потери качества: задача из
постановки — проезд случайных лабиринтов без столкновений — решена (одна
неудача на 1000 эпизодов, и та по лимиту времени).

Подвижные препятствия — задача другого класса. Без дообучения политика
сталкивается с ними в 28 % эпизодов: в обучающих данных не было ничего, что
двигалось бы само. Обучение с препятствиями (`--obstacles 2`, те же 4 млн шагов)
снижает эту долю до 20 %, но не устраняет её. Наблюдения согласуются с двумя
причинами.

1. **У политики нет памяти.** Она получает один скан, а по одному скану нельзя
   оценить скорость объекта — приближающийся диск неотличим от удаляющегося.
   Выученная стратегия сводится к осторожности: ехать медленнее и держаться
   дальше от всего, что похоже на диск. Отсюда и плата в статических лабиринтах
   (2.3 % эпизодов не укладываются в лимит шагов, средняя длина эпизода 199 шагов
   против 160). На проверочных лабиринтах доля успеха достигает 75–80 % уже к
   0.7 млн шагов и за оставшиеся 3.3 млн не растёт (сохранённые веса — как раз с
   отметки 0.66 млн) — признак того, что упор в наблюдение, а не в оптимизацию.
2. **Препятствия не уступают дорогу.** В проходе 1.2 м роботу и диску (оба
   диаметром 0.4 м) остаётся на двоих 0.2 м зазора, и часть столкновений — наезд
   препятствия на робота, которому некуда деться. От них не свободен и
   классический стек с явной оценкой скоростей (раздел 10.2): в таких же
   лабиринтах с двумя препятствиями без касаний проходят 168 эпизодов из 200.

Первая причина устранима, и это естественное развитие работы: дать политике
информацию о движении — несколько сканов, разнесённых во времени (за один такт
0.05 с препятствие смещается не более чем на 2.5 см, что сравнимо с шумом
лидара, поэтому соседних сканов недостаточно), вместе с перемещением робота
между ними по одометрии, либо рекуррентный слой. Ядро симулятора для этого
менять не нужно: достаточно хранить историю наблюдений в скрипте обучения.
Вторая причина — свойство самой постановки и ограничивает любой метод.

эпизодах, имеет стандартную ошибку $\sqrt{p(1-p)/n}$: для 170 эпизодов из 200 это

двух стандартных ошибок ниже называются незначимыми и выводов из них не
делается. Прогон на 50 эпизодах (значение `--episodes` по умолчанию) даёт те же
эпизоды с номерами 1–50; для сравнения вариантов его недостаточно.

### 10.2. Навигационный стек

Карта заранее не известна, сенсоры с шумом по умолчанию, 200 эпизодов на строку
(у каждого свой мир), лимит 4000 шагов (200 с). Касание эпизод не обрывает.
«Без касаний» — цель достигнута и за весь эпизод робот ничего не задел; ошибка
позы — расстояние между оценкой положения и истинным положением в конце
эпизода, в среднем по эпизодам.

**Статичные лабиринты** 5 × 5 ячеек (7.2 × 7.2 м), проходы 1.2 м:

| Конфигурация | Цель достигнута | Без касаний | SPL | Ошибка позы | Перепланирований на эпизод |

| SLAM + Theta* + DWA (по умолчанию) | 200/200 | 200/200 | 0.938 | 2.2 см | 16.1 |
| A* со спрямлением вместо Theta* | 200/200 | 200/200 | 0.948 | 2.2 см | 14.8 |
| без поправки на угол падения (раздел 7.3) | 198/200 | 198/200 | 0.930 | 2.1 см | 17.6 |
| без сопоставления сканов | 156/200 | 156/200 | 0.742 | 18.9 см | 25.8 |
| чистая одометрия (для сравнения) | | | | 18.8 см | |

Качество восприятия в тех же прогонах. Для каждой истинной клетки поверхности
стены, которую робот наблюдал (158 тыс. клеток на строку), проверяется состояние
клетки карты, содержащей её центр. Мир статичен, поэтому любой объект, который

| Конфигурация | Клеток стен на карте занято | свободно (ошибка) | Тактов с ложным подвижным объектом |

Остальные клетки стен на карте числятся неразведанными: сетка карты сдвинута
относительно сетки мира, и отражения от поверхности стены часто ложатся в
соседнюю клетку карты, а не в ту, что содержит центр клетки стены.

**С подвижными препятствиями** (радиус 0.2 м, скорости 0.2–0.5 м/с; они не
уступают дорогу и не толкают робота):

| Мир | Препятствий | Цель достигнута | Без касаний | Касаний всего |
| --- | --- | --- | --- | --- |
| Арена 9 × 9 м с неподвижными препятствиями | 5 | 200/200 | 193/200 | 8 |
| Лабиринт, проходы 1.8 м | 4 | 200/200 | 184/200 | 19 |
| Лабиринт, проходы 1.2 м | 2 | 200/200 | 168/200 | 52 |
| Лабиринт, проходы 1.2 м | 4 | 198/200 | 133/200 | 137 |
| Всего | | 798/800 | 678/800 (84.8 %) | 216 |

Для каждого из 216 касаний записано, кто сближался и что робот знал о
препятствии:

* в 214 случаях скорость робота в сторону препятствия была ниже 0.1 м/с (средний
  модуль скорости робота в момент касания — 0.02 м/с): робот стоял или отъезжал,
  а препятствие въезжало в него;
* во всех 216 случаях препятствие находилось в прямой видимости дольше секунды и
  сопровождалось трекером как подвижное;
* 5 касаний произошли в первые три секунды эпизода, когда карта вокруг ещё не
  построена и трекер не может отличить едущий навстречу объект от стены;
* касаний стен нет.

Таким образом, причина касаний — не восприятие, а геометрия и правила сцены. В
проходе 1.2 м роботу и диску (оба диаметром 0.4 м) остаётся на двоих 0.2 м
зазора, и препятствие, которое не уступает дорогу, в тупике или узком месте
объехать нельзя: на тесный лабиринт с четырьмя препятствиями приходится 137
касаний из 216, причём распределены они неравномерно — робот, зажатый в тупике,
получает несколько касаний подряд. С расширением прохода до 1.8 м без касаний
проходят 92 % эпизодов, на открытой арене — 96.5 %.

**Сравнение вариантов.** Три механизма проверены включением и выключением на тех
же 800 эпизодах с подвижными препятствиями и на 600 эпизодах в статичных
лабиринтах (три конфигурации стека с сопоставлением сканов). Каждая строка
воспроизводится указанным ключом `roversim_nav_bench`.

| Вариант | Статичные: цель достигнута | Ошибочно свободных клеток стен | Ложный подвижный объект, тактов | С препятствиями: без касаний | из них касаний в первые 3 с |
| --- | --- | --- | --- | --- | --- |
| по умолчанию | 598/600 | 1.6 % | 0.03 % | 678/800 | 5 |
| без памяти попаданий (`--hit-memory 0`) | 593/600 | 2.8 % | 0.19 % | 690/800 | 5 |
| с правилом смещения (`--confirm-travel 0.15`) | 598/600 | 1.6 % | 0.00 % | 670/800 | 7 |
| со стартовой паузой (`--startup-time 1`) | | | | 682/800 | 2 |

Что из этого следует.

* Память попаданий (раздел 7.1) делает то, для чего введена: карта почти вдвое
  реже теряет стены (и это видно в каждой из трёх конфигураций), а неудач в
  статичных лабиринтах становится 2 вместо 7 — 0.3 % против 1.2 %, различие в
  1.7 стандартной ошибки, то есть на границе значимости. В сценах с
  препятствиями эпизодов без касаний при этом на 12 меньше (1.5 п. п. при
  стандартной ошибке разности 1.8 п. п.) — различие незначимо, но направление
  стоит иметь в виду: возможная причина в том, что препятствие, увиденное в ещё
  не разведанной области, неотличимо от стены и задерживается на карте дольше.
* Правило смещения (раздел 8.4) убирает ложные подвижные объекты, но уходу от
  настоящих препятствий не помогает; по умолчанию выключено.
* Стартовая пауза (раздел 8.6) сокращает касания в первые секунды эпизода, но
  общий результат не меняет; по умолчанию выключена.

**Что не помогло в тесных проходах.** В 44 касаниях из 51 (выборка из 60 эпизодов) робот в момент контакта
стоит: DWA отвергает траектории ухода, потому что перед прогнозируемым касанием
«не успеть остановиться», и остаётся только поворот на месте. Проверены две
поправки (в код не вошли; те же 800 эпизодов):

| Поправка | Без касаний | Касаний | Побочный эффект |
| --- | --- | --- | --- |
| исходный вариант | 678/800 | 216 | |
| считать допустимой траекторию, которая не хуже остановки (касание не раньше, чем у стоящего робота) | 682/800 | 234 | в 138 касаниях робот сам сближался, средняя скорость робота при касании 0.38 м/с вместо 0.02; 20 касаний стен |

Доля эпизодов без касаний не изменилась ни в одном случае. Первая поправка лишь
превращает «препятствие въехало в стоящего робота» в «робот на ходу столкнулся с
препятствием», что хуже. Вывод: в проходе, где препятствие занимает всё
свободное место и не уступает дорогу, результат определяет геометрия, а не
локальный планировщик. Улучшить его может только уровень выше — глобальный
маршрут, который учитывает подвижные объекты и заранее уходит в боковой проход
или не заезжает в тупик им навстречу.

**Время.** Такт навигатора занимает в среднем 0.5 мс при периоде управления
50 мс — запас по времени стократный. Вместе с шагом симулятора замкнутый контур

## 11. Ограничения и направления развития

**Модель робота.** Корпус — круг, центр масс — в середине ведущей оси, вес
распределён между колёсами поровну и не перераспределяется при разгоне. Стены
без трения. Естественные расширения: смещённый центр масс и опорное колесо,
прямоугольный корпус, трение о стены.

**Сенсоры.** Лидар снимает скан мгновенно; искажение скана из-за движения робота
за время оборота не моделируется. Нет зависимости шума от угла падения и
отражающей способности.

**SLAM.** Нет замыкания циклов и глобальной оптимизации; на длинных маршрутах по
новой территории ошибка медленно растёт. Сопоставление локальное: при ошибке
прогноза больше нескольких сантиметров оно может не сойтись. Карта имеет
фиксированный размер (по умолчанию 20 × 20 м с центром в точке старта) и не
растёт. Клетка 5 см сравнима с ошибкой позы, поэтому тонкие элементы — торцы
стен толщиной 0.2 м — карта воспроизводит хуже всего: 1.6 % клеток поверхности
стен ошибочно числятся свободными. Расширения: корреляционное сопоставление в
окне, граф поз, прокручиваемая карта.

**Подвижные препятствия.** Трекер выделяет подвижные объекты сравнением скана с
картой, поэтому ему нужен уже разведанный «пол»: в первую секунду после
включения и в только что открывшихся областях движущийся объект неотличим от
стены. Объекты считаются компактными (до 1 м), а их движение — прямолинейным.
Глобальный планировщик подвижные препятствия не учитывает. Препятствия в
симуляторе не уступают дорогу, и в проходе, где препятствие занимает всё
свободное место, касания избежать нельзя: в лабиринте с проходами 1.2 м и
четырьмя препятствиями без касаний проходят две трети эпизодов.

**Обучение.** Политика не имеет памяти и опирается на подсказку маршрута; для
работы без неё нужна рекуррентная политика или карта в наблюдении. По одному
скану нельзя определить скорость препятствия — для уверенного объезда подвижных
объектов в наблюдение следует добавить предыдущий скан.

**Платформа.** Разделяемая память использует POSIX и futex (Linux; на macOS —
опрос). Один управляющий клиент на сегмент.
